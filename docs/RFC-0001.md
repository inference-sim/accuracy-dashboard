# RFC-0001: BLIS Accuracy Dashboard (v0.1.0)

**Status:** Draft / Request for Comments · **Target:** v0.1.0 · **Author:** @susiejojo · **Date:** 2026-10-15

A proposal for a dashboard that reports **how accurately BLIS predicts real inference latency**, scored nightly against [SemiAnalysis InferenceX](https://inferencex.semianalysis.com). Inspired by the [NVIDIA AISimulate e2e-accuracy dashboard](https://ai-dynamo.org/aisimulate/e2e-accuracy/) and [inference-sim/leaderboard](https://github.com/inference-sim/leaderboard).

---

## 1. Summary

Build a dashboard reporting **how accurately BLIS predicts real inference latency**, scored nightly against InferenceX. We report **MAPE** (absolute level error) and **SHAPE** (normalized concurrency-curve error), broken down by model, hardware and workload — **every number from a full BLIS end-to-end run, never the kernel in isolation**.

- **BLIS only** — this is an accuracy report, not a multi-simulator leaderboard.
- **End-to-end only** — every comparison uses a full `blis run`/`replay`, so scheduler/admission/batching drift is visible (§4.3). No kernel-only scoring.
- **Per-point data comes from `cmd/signedprobe`** — a per-point exporter already in the release (one CSV row per point: scenario, model, gpu, label, concurrency, measured + predicted TTFT & TPOT, tier). **No upstream change, no PR, no `-json`.** **`signedprobe` is the single source of truth** — its semantics *are* the definition of the dashboard's numbers (§4.3). It is not reconciled numerically against `metricscore`; the two legitimately compute different things.
- **Metrics: mean TTFT and TPOT, each MAPE + shape** — exactly what `signedprobe` emits at the pinned release. **E2E, tail p99 and throughput are not in v0.1.0 at all** (not shown, not gated); a one-line note says they come later, once the harness/extractor carry them (§4.3a, §7).
- **Tiers:** **MEASURED-OR-RESOLVED** (apples-to-apples) and **ALL (approximate)** — both carried in the data, shown one at a time via a tier switch.
- **No quality exclusions in v0.1.0** — every point `signedprobe` emits is scored and shown. We apply no filtering (keeping scoring logic out of this repo); the few known measurement artefacts (e.g. 4 gpt-oss-120b/h200 TTFT spikes, non-monotone-TPOT sweeps) are listed in a "known artefacts" note, not dropped. **Multi-node** is a toggle, hidden by default, scored when enabled (needs a kernel-repo change — may ship disabled).
- **Default view is on-target vLLM** (`v0.31.0`): with version as a filter and no banded group, the default state *is* the headline, so it must not pool off-version measurements. "all" is one click away (§6.3).
- **CI resolves the latest BLIS release at run time — no version is hardcoded in this repo.** It always scores whatever the current latest stable release is (never `main`, never a pre-release), and a brand-new release is picked up automatically on the next nightly run with no change to this repo.
- **Nightly CI** re-runs the evaluation; ground truth is pinned to the **latest weekly InferenceX db-dump Release**. A run also triggers whenever CI resolves a **newer BLIS release tag**.
- **UI:** **Overview page only, no plots** — two tables mirroring AISimulate: a summary drill-down (model → workload → GPU → topology) and a points table (measured vs predicted per concurrency) for the selected row. Hosted on **GitHub Pages**, data committed to the repo. No Go server, no RITS/OpenShift deployment.
- InferenceX is the first and only ground-truth source; the schema reserves room for **llm-d-prism** and **vLLM benchmark** data later.

## 2. Background and prior art

### 2.1 What already exists (and what we reuse)

**We score BLIS end to end — never the kernel in isolation.** The kernel-only scorers in
`blis-latency-kernel` (`cmd/score`, `cmd/shape`) can't see drift from BLIS's scheduler, batch
formation or admission, and refuse TTFT by design. The end-to-end machinery already exists in
[`inference-sim`](https://github.com/inference-sim/inference-sim): `sim/kernelmodel/harness` runs
`blis replay` on the benchmark client's main phase (seed-0 request lengths, concurrency gating, the
run's own engine flags) and computes measured-vs-predicted **TTFT and TPOT** per point.

The piece that makes the drill-down possible: **`cmd/signedprobe` already emits the per-point
rows** we need — no new flag, no `-json`, no upstream change. (Verified: built at `v0.1.0`'s kernel +
ran it end-to-end — one CSV row per point.) What we reuse, and where it lives:

| Component | Repo | What it does | Reuse |
|---|---|---|---|
| `cmd/signedprobe` | **inference-sim** | **Per-point exporter.** One CSV row per point: `scenario, model, gpu, label, concurrency, meas_tpot_us, pred_tpot_us, meas_ttft_us, pred_ttft_us, tier` — from a real `blis replay`, AISimulate-free. | **The evaluator's data source.** Built from source at the pinned tag; we only orchestrate it — no scoring logic, no edits. |
| `cmd/metricscore` | **inference-sim** | Aggregate scorer (per tier / chip / model / framework). | **Not consumed for numbers.** Optionally logged as a loose, non-blocking ballpark diagnostic (§4.5); never an equality gate — it drops whole sweeps on a single bad point and tiers without the warm-up bracket, so its aggregates differ from `signedprobe`'s by design. |
| `scripts/extract_inferencex_direct.py` + `gen_direct_corpus.py` | **blis-latency-kernel** | Reads the InferenceX dump directly (849 deployments, ~3,345 points, keyed on each run's server-log args) and writes the corpus + scenarios `signedprobe`/`metricscore` consume. | Nightly **ingest**. |
| `extract_inferencex_engine_settings.py` | **blis-latency-kernel** | Per-run engine launch flags (`-engine-settings`) — configures each simulated point as the measured run was launched. Also records each run's logged `engine_version` (see D1). | Ingest. |

**No new extraction scripts, no new scorer, and no upstream PR are needed** — the direct extractor
writes the corpus `signedprobe` consumes, and `signedprobe` already emits the per-point
measured/predicted TTFT & TPOT the drill-down is built from.

### 2.2 Data release schedule for InferenceX, and how AISimulate consumes it (confirmed)

- **Cadence:** ~**1,000+ new benchmark datapoints per week**; the full database is **published as a public GitHub Release every week**.
- **Location:** `github.com/SemiAnalysisAI/InferenceX-app/releases/tag/db-dump/YYYY-MM-DD` (currently `db-dump/2026-09-28`), each pinned by a `measurement_sha256`.
- **Shape:** a restorable Postgres dump; the evaluator needs only `benchmark_results`, `configs`, `workflow_runs`.
- **Also available:** a credential-free public JSON/CSV API under `https://inferencex.semianalysis.com/api/v1/...`. We treat the **weekly release as source of truth** (reproducible, sha-pinned) and keep the API as a fallback / cross-check.

**How AISimulate does it — verified from their live `summary.json`:**

```
measurement_source       = SemiAnalysis InferenceX
measurement_source_url    = .../InferenceX-app/releases/tag/db-dump/2026-09-28   ← weekly Release
release_tag               = db-dump/2026-09-28
measurement_date_through  = 2026-09-27
aisimulate_completed_at   = 2026-10-15T11:12:57Z                                 ← regenerated today
selection_policy          = latest-complete-config-run-v1
```

The two timestamps are the whole point: AISimulate **pins a weekly db-dump Release** (data frozen through 2026-09-27) and **regenerates the dashboard against that pinned snapshot frequently (nightly)** — it does **not** chase InferenceX's intra-week commits. **We adopt the identical behavior:** nightly re-run, ground truth = the latest weekly InferenceX Release. The InferenceX "diff" is the weekly tag bump; the BLIS "diff" is a new release tag.

> For reference, AISimulate's current headline numbers against this snapshot: `tpot_mape 22.39%`, `tpot_shape_error 11.83%`, `ttft_mape 45.27%`, coverage 76.48% over 1584 points. (TTFT MAPE ~2× TPOT — TTFT is the harder, queue-dominated metric.)

## 3. Goals / Non-goals

**Goals**
1. Nightly, reproducible BLIS accuracy numbers vs InferenceX, with full provenance.
2. Mean **TTFT and TPOT**, each MAPE + shape, end-to-end — the metrics `signedprobe` emits. E2E/tail/throughput are out of scope for v0.1.0 (not shown), noted as future work.
3. Overview = two tables (summary drill-down model → workload → GPU → topology, run-wide counts, + a points table per selected row), sortable, with a tier switch.
4. Re-evaluate nightly; ground truth pinned to the latest weekly InferenceX Release; also trigger on a new BLIS release.
5. Score the **latest stable BLIS release**, resolved by CI at run time (never hardcoded in this repo); `main` and pre-releases are explicitly excluded.
6. Pluggable ground-truth sources (InferenceX now; prism / vLLM later).

**Non-goals**
- Not a multi-simulator leaderboard — **BLIS only**.
- **No plots in v0.1.0** — tables only; latency/trend charts are deferred.
- **No server / no RITS / no OpenShift** — static site on GitHub Pages, data in the repo.
- No universal pass/fail threshold (follow AISimulate: numbers apply only to the exact measured operating points in a snapshot).
- Not re-deriving InferenceX measurements; we consume their published weekly dump.
- Not tracking InferenceX intra-week commits (neither does AISimulate).

## 4. Design

### 4.1 High-level architecture

```
                   ┌──────────────────────────────────────────────────────┐
                   │  Nightly CI (GitHub Actions, scheduled + dispatch)     │
                   │                                                        │
  InferenceX ──────┤  1. detect-diff:  latest weekly db-dump tag vs state  │
  weekly release   │                   latest BLIS tag          vs state   │
                   │                   → noop if both unchanged             │
  BLIS release ────┤  2. ingest:       restore dump → direct extractor     │
  (resolved tag)   │                   → corpus + scenarios (sha-pinned)   │
                   │  3. evaluate:     build blis + signedprobe FROM SOURCE │
                   │                   at $BLIS_TAG (never main/pre-release)│
                   │                   → signedprobe: blis replay per point │
                   │                   → per-point meas/pred TTFT & TPOT    │
                   │                   (MAPE+shape recomputed client-side)  │
                   │  4. publish:      data/ committed to the SAME branch   │
                   │                   GitHub Pages serves (gh-pages)        │
                   └───────────────────────────┬────────────────────────────┘
                                                │  fetch('data/latest/summary.json')
                   ┌────────────────────────────▼───────────────────────────┐
                   │  Static site on GitHub Pages (site + data, one branch)  │
                   │  - plain static SPA, fetches data/latest/summary.json   │
                   │  - renders Overview = tables only, no plots             │
                   │  - no server, no DB, no RITS/OpenShift deployment       │
                   └─────────────────────────────────────────────────────────┘
```

### 4.2 Backend — none; static JSON committed to the repo, served by GitHub Pages

**Decided: GitHub Pages + data in the repo. No Go server, no RITS/OpenShift deployment for now.**
There is no backend service. The nightly CI job commits the data JSON to the repo; a static SPA on
GitHub Pages fetches and renders it client-side.

- **One branch, served by Pages (resolves the earlier ambiguity).** CI commits data **to the same
  branch GitHub Pages serves** — the SPA and its data ship together, so `fetch('data/latest/summary.json')`
  is a plain same-origin request with no cross-branch indirection. (Concretely: Pages serves `gh-pages`;
  CI commits both the built site and `data/` there. We do **not** keep a separate "data branch" the
  site can't see.)
- **Layout on that branch.** `data/latest/summary.json` is the current snapshot; `data/snapshots/<run_id>/summary.json`
  keeps the history. Each snapshot is an immutable, self-describing JSON file (provenance block, §4.4).
- **No API.** The site reads the committed JSON directly. A "Download JSON" link points at that same
  file (parity with AISimulate's `summary.json`).
- **Why this over the earlier Go-server plan:** the dashboard is read-only, single-simulator, and
  publishes a small summary once a night — a server, a container image and a PVC earn nothing here.
  GitHub Pages is zero-ops and the data is versioned in git for free (every nightly commit is an
  auditable history of the numbers). If we later need server-side filtering over many snapshots we
  can revisit, but v0.1.0 does not.

### 4.3 Evaluator — end-to-end per-point, via `cmd/signedprobe`

**Every number is from a full BLIS end-to-end run — we never score the kernel in isolation.**
The evaluator runs `inference-sim`'s **`cmd/signedprobe`**, which `blis replay`s each in-scope
InferenceX point through the whole stack (router/admission → scheduler → batch formation → kernel)
and writes **one CSV row per point**:

```
scenario, model, gpu, label, concurrency, meas_tpot_us, pred_tpot_us, meas_ttft_us, pred_ttft_us, tier
```

From those per-point rows the orchestration computes **MAPE and shape for TTFT and TPOT**, and the
dashboard recomputes every aggregate client-side (§4.5). That is the whole v0.1.0 metric set.
**E2E, tail p99 and throughput are not in v0.1.0 at all** — `signedprobe` doesn't emit them (neither
the harness `Observation` nor the extractor carries them); they are simply absent, with a one-line
"added later" note (§4.3a), not shown as empty/gated columns.

Shape error is the *end-to-end* concurrency response (each side re-anchored at the sweep's **lowest
surviving** concurrency — since partial sweeps are kept, **both sides anchor at the same surviving
point**, never at different concurrencies; the sweep is flagged when its original lowest point is
missing, and a sweep left with <2 points gets `shape = null` with a reason). It is not the kernel's
StepTime ratio — so it
captures scheduler and batching effects a kernel-only shape cannot. In-scope subset: `single_turn`
sweeps (`agentic_traces` rows
carry NULL isl/osl).

**`signedprobe` is the single source of truth, and its semantics *are* the definition** — stated
once, in provenance and the schema's "what the numbers mean" note: per-point; tier **without** the
warm-up bracket (its column is `tier_unbracketed`, so a prefix-caching point reads `ALL` here where
`metricscore` might bracket it stricter); and a partially-failing sweep keeps its good points rather
than being dropped whole. The dashboard **does not reconcile against `metricscore`** — the two
compute different things by design (whole-sweep-drop + warm-up bracket), so an equality check would
be drift-by-construction. Correctness is instead checked *self-consistently* (§4.5): the dashboard's
client-side aggregates are re-derived a second, independent way from the *same* `signedprobe` rows
and asserted equal — testing our arithmetic, not a second tool. No scoring code is written in this
repo — `signedprobe`, the `blis replay` harness and the tiering already exist in the release. *(Verified: built `blis` + `signedprobe` at the pinned `blis-latency-kernel@v0.1.0` and ran
`signedprobe` end-to-end on a direct-format corpus with three real `blis replay`s — it emitted the
per-point CSV above, measured + predicted TTFT & TPOT with the tier, AISimulate-free. It requires
`-scenarios` set explicitly, which is exactly the all-flags-explicit discipline the pipeline uses.)*

**Which BLIS release — CI resolves it, the repo never hardcodes it.** There is **no release
version written anywhere in this repo**. On every run the CI job *discovers* the current latest
stable BLIS release at run time and uses whatever that is:

```bash
# BOTH inputs are resolved by CI each night — not committed, not hand-edited
BLIS_TAG=$(gh release list --repo inference-sim/inference-sim \
             --exclude-drafts --exclude-pre-releases -L1 \
             --json tagName -q '.[0].tagName')     # e.g. v0.10.0 today, v0.11.0 whenever it ships
IX_TAG=$(gh release list --repo SemiAnalysisAI/InferenceX-app \
             --exclude-drafts --exclude-pre-releases \
             --json tagName -q '[.[].tagName | select(startswith("db-dump/"))] | first')  # latest weekly dump
             # the db-dump/ filter is load-bearing: the repo's newest release is often an unrelated
             # "InferenceX skills" tag, not a dump.
```

So when **either** BLIS cuts a new release **or** InferenceX publishes a new weekly dump, the next
nightly run picks it up automatically — no PR to this repo, no config change. Neither side is
hardcoded. "Pinned" means only that **a single run freezes onto the pair of resolved tags** (for
reproducibility and provenance), *not* that a version is fixed in the codebase. The evaluator then
checks out that exact tag and **builds `blis`, `signedprobe` and `metricscore` from source** at it
(they are not in any published image — the `Dockerfile` builds only `blis`), records the tag + build
commit in the provenance block, and makes the tag part of the snapshot id. It **never** builds `main`
and **never** uses a pre-release. The newly-resolved tag differing from `state/last-run.json` is
exactly what triggers a fresh evaluation (§4.6).

**Architectural rule: build/run upstream at the pinned tag, never vendor or edit it.** This repo
holds only *orchestration and presentation* — not a copy of any scorer or extractor:

- `signedprobe` and `metricscore` are **built from source at the resolved tag** (`go build
  ./cmd/signedprobe ./cmd/metricscore` + `go build -o blis main.go` in the checkout — which also keeps
  the harness's vendored `testdata/` catalog/registry defaults resolvable). We don't fork, patch, or
  add flags: they must stay the *same* version as the `blis` they drive. **No upstream PR, no `-json`,
  no branch** — `signedprobe`'s existing CSV is the per-point source.
- The **extractors** (`extract_inferencex_direct.py`, `gen_direct_corpus.py`,
  `extract_inferencex_engine_settings.py`) run at the **`blis-latency-kernel` version BLIS's `go.mod`
  pins** (recorded as `extractor_version`), tracking the release and the dump schema. Not copied here.
- What lives in this repo: the CI workflow, the `(blis_tag, ix_tag)` diff/state logic, the shaping of
  `signedprobe`'s CSV into `summary.json`, and the static site. The glue, not the science.

### 4.3a Metrics NOT in v0.1.0 (E2E, tail p99, throughput)

**v0.1.0 reports mean TTFT and TPOT only — the two metrics `signedprobe` emits.** E2E, tail p99 and
throughput are **not shown at all** — no column, no gated/placeholder cell, nothing. The page carries
a single line: *"E2E, tail-latency and throughput accuracy are planned for a future release."*

The reason they're absent rather than gated: both the predicted side (harness `Observation`, which
carries only `MeanTTFTUs`/`MeanTPOTUs`) and the measured side (the direct extractor's `SELECT`, which
pulls only `mean_tpot`/`mean_ttft` from the dump) would each need widening — a two-repo change
(`inference-sim` + `blis-latency-kernel`) that, by the version-lag rule (§4.4), can only reach a
dashboard through a *future* release. Rather than ship empty columns promising numbers we can't yet
produce, we omit them and name them as future work (§7). When they're added, tail is MAPE-only (a
level/SLO question) and throughput is per-GPU-normalised.

### 4.4 `summary.json` schema (draft)

**Where this schema lives: local to this repo for v0.1.0.** `summary.json` is defined and versioned
here (`schemas/summary.v1.json`), validated in CI by `schema_version` so a format break is caught
before the static site renders garbage. We **consume the pinned release's scorer output as-is** —
the corpus/score types ship *inside* the release (`harness.Corpus` is a local type in `inference-sim`,
versioned with the binary), so the dashboard takes whatever that release emits and shapes it; it does
not get to change a format in a release that already exists.

**Why not standardize in `blis-schemas` now — the version-lag reality.** `blis-schemas` does host the
measurement side (`spec/evaluation`), so it would be the *natural* long-term home for a shared
comparison record. But the dashboard scores an **already-shipped, pinned release**, and that release's
`go.mod` pins a *specific older* `blis-schemas` (today: release `inference-sim v0.10.0` → `blis-schemas
v0.2.2`, while schemas head is already `v0.3.0`). A schema change can therefore never be a dependency
of a release that exists — only of a future one, three hops out:

```
new type in blis-schemas → a FUTURE inference-sim release bumps go.mod + emits it → weeks later the dashboard's CI resolves that release
```

So blis-schemas standardization is a **decoupled, forward-looking upstream effort, explicitly NOT a
v0.1.0 dependency** (and `spec/evaluation` has no consumers yet today). v0.1.0 ships with the local
wrapper only; adopting `spec/evaluation` for the corpus and adding a comparison record upstream is a
post-0.1.0 follow-up that benefits later releases on schemas' own cadence.

The matrix is a **drill-down tree** — model → workload → gpu → topology, with **point** leaves under
each topology — mirroring AISimulate's `summary.json`. In the UI the *summary table* renders the
tree down to **topology**; selecting a topology row renders its **points** in the second table (§4.5).
Every node carries its own coverage and a metric block **per tier** (`measured_or_resolved` and
`all`); the leaf point carries BLIS's predicted vs the measured value. vLLM version and
`is_multinode` live on the node.

**Aggregates are computed from the leaf points, not stored-and-frozen (point 1).** The precomputed
node `metrics` are valid only for the *unfiltered* tree; the moment the UI's version filter,
hardware filter or multi-node toggle hides some points, every parent aggregate and shape error above
them would be stale. So the client **recomputes aggregates from the visible leaf points** (shape
included, which is why each sweep's points must be present client-side). Precomputing per
filter-combination is not viable now that hardware is also a filter. The stored node `metrics` are a
convenience for the default (unfiltered, on-target) view; any non-default filter recomputes.

**Maintainability — three rules that keep this from rotting across BLIS releases:**
1. **One source of truth.** `signedprobe`'s per-point CSV is the only input; its semantics (above)
   are the documented definition of every number. No second tool is a numeric authority.
2. **Self-consistency oracle (asserted) + metricscore comparison (logged).** The hard CI assertion
   is self-consistency: re-derive the dashboard's client-side aggregates a second, independent way
   from the *same* CSV rows and assert they match — this tests our aggregation arithmetic, needs no
   second tool, and **never drifts**. Separately, the `metricscore` aggregate comparison is **logged,
   non-blocking**: the two tools score identical per-point *values* (both call the same
   `harness.Run`; warm-up is "information only", never scored), so they differ only on three known
   edge-sets — (a) points kept on a partially-failing sweep (`signedprobe` keeps them, `metricscore`
   drops the whole sweep); (b) points with a measured TPOT but no measured TTFT (`signedprobe` drops
   them, `metricscore` still scores their TPOT); (c) the tier *label* on prefix-caching points
   (`signedprobe` is unbracketed). The logged gap is therefore *expected to equal those three
   edge-sets' point counts* — and the first
   production run **quantifies** it (we don't yet know how many InferenceX points enable prefix
   caching; benchmark runs commonly disable it, but the dump decides). It's a measurement, not a gate.
3. **Pin the one external contract, fail loud.** The only thing that can change under us is
   `signedprobe`'s CSV header at a future tag. The pipeline asserts the expected header and **fails
   the run with a clear message** if it changed ("signedprobe columns changed at `<tag>` — update the
   parser"), rather than silently mis-parsing. Same discipline as `schema_version` on `summary.json`.

**A `totals` node sits above the models (point 2)** — the headline "BLIS TPOT MAPE is X% over N
points", per tier, which the model-rooted tree otherwise never states. Every level, `totals`
included, averages **individual point errors, not child-node means** (so a sparse sweep doesn't get
the same weight as a dense one). The `totals` row also shows the **same-points Δ vs the previous
snapshot visibly** (e.g. `14.2% ▼0.4`), not only on hover (point 3) — it's the "did this release
move accuracy?" number the project exists for, and hover doesn't survive touch/screenshot/print. On
the **first snapshot** (no previous to diff) the Δ renders `— (first snapshot)`.

```jsonc
          "same_points_delta": { "tpot_mape": -0.4, "ttft_mape": +1.1, "n_intersect": 17 }   // Q6
        },
        "all": { "mape": {}, "shape": {}, "noise_floor_pct": 2.3 }
      },
      "rows": [                                   // workload → gpu → topology → point
        { "level": "workload", "label": "1024:1024", "coverage": {"scored":55,"total":64}, "metrics": {}, "rows": [
          { "level": "gpu", "label": "H200", "precision": "MXFP8", "coverage": {"scored":28,"total":31}, "metrics": {}, "rows": [
            { "level": "topology", "framework": "vllm", "engine_version": "0.31.0", "on_target_version": true,
              "is_multinode": false, "parallelism": {"tp":8,"ep":8,"pp":1}, "serving": "aggregated",
              "spec_method": "none",                       // "mtp" sweeps → not_scored:no_acceptance_rate in v0.1.0 (below)
              "coverage": {"scored":8,"total":8}, "metrics": {}, "rows": [
              { "level": "point", "concurrency": 64,
                "measured":  { "ttft_ms": 821, "tpot_ms": 13.2 },
                "predicted": { "ttft_ms": 980, "tpot_ms": 15.1 },
                "error_pct": { "ttft": +19.3, "tpot": +14.8 },
                "shape": { "ttft": +9.4, "tpot": +1.9 } },  // null when the sweep has < 3 concurrencies
              { "level": "point", "concurrency": 256, "shape": null, "shape_reason": "< 3 concurrencies" }
            ]}
          ]}
        ]}
      ]
    }
  ],
  "scope": { "multinode": "toggle (hidden by default; may be disabled in v0.1.0)",
             "measured_exclusions": ["ttft_spike", "non_monotone_tpot_sweep"],
             "vllm_version_filter": "on-target" }   // DEFAULT is on-target, not all (§6.3)
}
```

- **`noise_floor_pct` is per row, computed from the measurement** (InferenceX `std_*` and repeat
  runs), not the extractor's corpus-wide 1.6% median — that constant is a documented **fallback
  only**, used when a row has no repeats. Noise is much larger at concurrency 1–4, which a single
  constant would hide.
- **`same_points_delta`** is the change vs `previous_snapshot_id` over the **intersection of points
  both snapshots scored** — the honest "did this BLIS release move accuracy?" number, with the
  point-set change held out (Q6).
- **`coverage`** counts every disposition, so not-scored/failed points are visible and never
  silently become zero error (D6). **Every in-scope corpus point is accounted for by comparing the
  corpus against `signedprobe`'s CSV rows** — a point `signedprobe` skipped (no measured absolute, a
  run error) is detected by that diff and recorded as `not_scored` with a reason; the pipeline never
  parses `signedprobe`'s stderr to find them. **`not_scored`** is one bucket for everything BLIS has
  no scenario for — model or hardware not in the catalog, or an engine BLIS can't model (e.g. not
  vLLM) — plus those skipped points, with a `not_scored_reasons` breakdown for whoever wants to close
  the gap (adding a catalog entry moves a deployment from `not_scored` to `scored`). `multinode_hidden` is how many points the multi-node
  toggle is currently hiding. There are **no quality exclusions in v0.1.0** — nothing is dropped for
  being an "outlier", a TTFT spike, or a non-monotone sweep (those would be scoring logic, which stays
  out of this repo). Known measurement artefacts are listed in `known_artefacts` for the reader, not
  filtered out.
- **Speculative (`mtp`) points are all `not_scored` in v0.1.0.** `blis run`/`replay` refuses a
  drafting scenario without an acceptance rate, the API doesn't publish one, and *any value we pick is
  a tuning knob* (forbidden by the no-tuning non-goal). Reading it from the run's server log is **new
  code in two repos** — the extractor doesn't capture it and the harness never passes
  `--speculative-acceptance-rate` to `blis replay` at `v0.10.0` — so by the version-lag rule it ships
  in a *future* release, exactly like E2E/tail (§7). **In v0.1.0, every `spec_method: mtp` point is
  `not_scored` with reason `no_acceptance_rate`**; we never assume a value, and the dashboard never
  parses server logs itself (that extraction belongs in the kernel repo's extractor — "glue, not the
  science"). About half the MiniMax-M3 deployments are `mtp`, so this is counted, not hidden.
- **Sweeps with < 3 concurrencies have no shape.** Shape needs ≥3 points; a 2-point sweep's `shape`
  is `null` with `shape_reason: "< 3 concurrencies"` (rendered `—`, not blank or 0), and its MAPE
  still counts.
- **`metrics`** names the v0.1.0 set (`["ttft","tpot"]`). E2E, tail and throughput are **not keys in
  the schema at all** — not present, not null, not gated. They appear only as a one-line "future
  work" note on the page (§4.3a).
- **vLLM version is a facet, not a group.** `target_vllm` records BLIS's priced version; each
  topology/point node carries its measured `engine_version` + `on_target_version`. The UI compares to
  `target_vllm` for the badge colour and the version filter — there is no `group` field and no banded
  "headline/off-version/retired" split (dropped per discussion). Retirement, if surfaced, is just a
  per-model note.
- **The leaf `point`** carries absolute `measured` and `predicted` values plus `error_pct`, so the
  drill-down bottoms out at BLIS-vs-InferenceX per concurrency — matching how AISimulate's points read.

### 4.5 Frontend — static SPA, **Overview page only, tables only, no plots**

**Decided scope for v0.1.0:** one page (Overview), two linked tables (summary drill-down + points),
**no plots** of any kind. We start with tables and can add charts later.

- **UI framework: reuse `inference-sim/leaderboard/web`.** Build on the leaderboard's existing
  [`web/`](https://github.com/inference-sim/leaderboard/tree/main/web) stack (Vite + its table and
  component conventions) rather than choosing a new one, so the two dashboards look and behave
  consistently and `/goal` doesn't pick its own framework.
- **Two tables, like AISimulate's Overview.** (1) A **summary drill-down** — one row per **model**,
  expandable through **workload → GPU → topology** — the same hierarchy AISimulate's `summary.json`
  uses; every level aggregates the levels under it. (2) A **points table** for the selected row,
  showing **measured vs predicted vs error** per concurrency (AISimulate's leaf view). Columns sort
  on click. No composite score, no pass/fail colouring.
- **Run-wide counts between the tables.** `models / points scored / not scored / multi-node (hidden)
  / failed` sit on one line below the summary table and above the points table — so the "failures
  never become zero errors" accounting is visible without a per-row coverage column cluttering the
  summary. (Per-row coverage is carried in `summary.json` and can be surfaced later; v0.1.0's UI keeps
  the summary to the metrics, with fidelity expressed by the tier. InferenceX's own config-quality
  flag is **not** carried in v0.1.0 — it was dropped with the per-point cfg indicator; the tier is the
  single fidelity axis.)
- **One tier at a time, switchable.** A `measured-or-resolved | all` switch rescopes the tables (not
  two columns per metric — that doubled the width). The tier is decided per sweep (same coverage
  logic the scorer uses).
- **Metrics (end-to-end from `blis replay`), stated in each header:**
  - **Mean TTFT, TPOT** — **MAPE and shape**. This is v0.1.0's full metric set (what `signedprobe`
    emits, §4.3a).
  - **E2E, Tail p99, Throughput** — **not shown at all** in v0.1.0. A single line below the table
    reads *"E2E, tail-latency and throughput accuracy are planned for a future release"* (§4.3a). No
    empty or gated columns.
- **No quality exclusions in v0.1.0.** `signedprobe` emits every point it can run and applies no
  filtering; the exclusions `metricscore` would apply (TTFT-spike points, non-monotone-TPOT sweeps)
  are **not** reimplemented here — that would be scoring logic, which stays out of this repo. Those
  known measurement artefacts (e.g. the 4 gpt-oss-120b/h200 TTFT spikes) are surfaced in a
  **`known_artefacts` note**, not dropped. Every scored point is shown; no prediction-based filter.
- **Multi-node: a toggle, off by default** (**may ship disabled in v0.1.0** — enabling it needs a
  `blis-latency-kernel` change to `extract_inferencex_direct.py`, which is a kernel-repo PR; if that
  lands post-0.1.0 the toggle is present but disabled, with `multinode_hidden` counting what it would
  show). When enabled, BLIS replays those deployments with the correct multi-node scenario (below).
- **vLLM version: a per-row badge + a filter, defaulting to on-target.** A row's model is identified
  from the run's server log / InferenceX config, **never** the display name (D7 — "Llama 3.3 70B" is
  the retired `llama70b` = Llama-3.1-70B-Instruct). Each row shows its measured vLLM version as a badge
  — green on BLIS's target (`v0.31.0`), amber off-target. **The default filter is on-target**, because
  with no banded group the default state *is* the headline and must not pool off-version measurements
  (§6.3); "all" is one click away. An off-target/retired model is a normal row with an amber badge, not
  a banded group.
- **Provenance header** (from the summary's provenance block): resolved BLIS release tag plus its
  pinned **catalog (0.2.1), kernel (v0.1.0) and registry (v0.1.1)** versions, the InferenceX dump
  tag, snapshot date, and a **Download JSON** link to `data/latest/summary.json`.
- **Last-successful-run note** (Q10): the page shows the timestamp of the last fully-successful run;
  a failed or partial nightly run publishes nothing and leaves the previous snapshot in place.
- **Derived-input marking** (optional, cheap): points whose context/batch was derived or that carry
  speculation get a small marker, since the corpus already records it per point.

**How multi-node is scored correctly when the toggle is on.** Multi-node is *not* a `blis replay`
command-line flag — the topology lives inside the **scenario** the harness writes and feeds to
`blis replay` via `--scenario`. So "send the args correctly" means the ingest path must build a
faithful multi-node scenario, not drop these rows:

1. The direct extractor stops filtering `is_multinode = false`, so multi-node deployments enter the
   corpus.
2. `gen_direct_*` emits each one's scenario with the real **node count** (`cluster.nodes > 1`), the
   correct **fabric** (the inter-node interconnect from the catalog), and the measured **placement /
   parallelism** (pp across nodes, tp/ep within), so the kernel prices the cross-node KV/collective
   transfers rather than assuming a single node.
3. `blis replay` then runs that scenario end-to-end exactly as for single-node — same flags, same
   trace, same metrics.

A multi-node deployment with no catalog fabric or an unexpressible placement is counted in
`coverage.not_scored`, never silently mis-scored as single-node.

*Deferred (post-0.1.0): latency plots, snapshot/trend charts, interactivity view. (The per-point view
is **in** v0.1.0 — it's the points table, §4.5.)*

### 4.6 Nightly CI (GitHub Actions)

```yaml
on:
  schedule: [{ cron: "17 6 * * *" }]   # nightly, off the :00 mark
  workflow_dispatch:
jobs:
  detect-diff:   # compare latest weekly db-dump tag + CI-resolved latest BLIS tag to state/last-run.json
  evaluate:      # needs: detect-diff, if: changed. build blis+signedprobe+metricscore from source at $BLIS_TAG → restore dump → DIRECT extractor + gen_direct_* → signedprobe (per-point CSV) → shape into summary.json

  publish:       # commit data/latest/summary.json to the Pages-served branch; nothing on a failed/partial run
```

- **Runner:** GitHub-hosted `ubuntu-latest` for the end-to-end pass (BLIS is CPU-only and deterministic — no GPU, by design). The `blis replay` over every in-scope point is the heaviest step (both `signedprobe` and `metricscore` replay every point); if it outgrows a hosted runner, move `evaluate` to a larger self-hosted runner while diff/publish stay hosted. The dump restore (~34 GB) is its own disk concern. **Under time pressure, the `metricscore` diagnostic may be skipped or run less often — `signedprobe`'s points are never cut** (it is the source of truth; `metricscore` is only the logged cross-check).
- **Diff mechanism:** `state/last-run.json` holds the last **`(blis_tag, ix_tag)`** — just the two inputs that are actually resolved independently. The catalog and registry are **not** separate axes: each BLIS release states its compatible catalog/registry (committed in `docs/getting-started/installation.md` as "Compatible blis-catalog release: `<tag>`" and pinned in the kernel's `testdata/upstream.lock`), so they are *derived from* `blis_tag`, not chosen per run. They are recorded in provenance for traceability (§4.4) but never diffed on. Each night the job **resolves both inputs live** — `gh release list --repo inference-sim/inference-sim` for the newest stable BLIS tag and `gh release list --repo SemiAnalysisAI/InferenceX-app` for the latest `db-dump/*` — and compares the resolved pair to the stored one; identical ⇒ noop. Nothing is a hand-maintained version pin: a new release on either side *becomes* the scored input automatically the next night. A cheap poll, no webhooks.
- **Dump access:** InferenceX dumps are public GitHub Releases; restore in-CI with `pg_restore` into an ephemeral Postgres service container, cache by `measurement_sha256` (re-ingest only on a new weekly tag), then run the **direct** extractor path only — `extract_inferencex_direct.py` + `extract_inferencex_engine_settings.py` + `gen_direct_corpus.py`. **Not** `extract_inferencex_absolutes.py` / `aisimulate_e2e.json` (that path ties ground truth to NVIDIA's artifact; see the D3 reply).
- **Filter to vLLM before scoring:** the corpus is restricted to `framework: vllm` before `signedprobe` runs. `signedprobe` has **no** `-framework` flag (unlike `metricscore`), so without this it would run every sweep — including trtllm/sglang deployments BLIS can't model — adding only run errors and wasted time.
- **Extractor + scenario version (Q7, Q8):** the extractor and `gen_direct_*` scripts are run at the **`blis-latency-kernel` version BLIS's `go.mod` pins**, so they ride the `blis_tag` in the diff key and are recorded in provenance (`extractor_version`). The scenario files the direct corpus needs are **generated in-pipeline from the current dump** (`gen_direct_*`), not read from the module's frozen `testdata/direct` — a new weekly dump brings new deployments, and any deployment still without a scenario is counted in `coverage.not_scored`, not silently dropped.
- **Flags fully spelled out (Q7):** the evaluate job passes `-corpus`, `-scenarios`, `-engine-settings`, `-absolutes` and `-blis` explicitly to `signedprobe` (and to `metricscore` for the logged diagnostic), all pointing at the freshly-extracted direct corpus/scenarios. **`-scenarios` has no default and `signedprobe` errors without it** (verified), so it must be set — which conveniently guarantees **nothing falls back to an AISimulate-derived default**.
- **Per-point output (no `-json` needed):** `signedprobe` already writes per-point CSV to stdout; the evaluator consumes it directly. No `-json` flag, no upstream PR, no `main` build — `signedprobe`, `metricscore` and `blis` are all built from source at the resolved `$BLIS_TAG`.
- **Failure semantics (Q10):** a failed or partial nightly run **publishes nothing** and leaves the previous validated snapshot in place; the page shows a "last successful run" timestamp. No partial snapshot is ever committed.

## 5. Extensibility: additional ground-truth sources

The corpus format (`point` with stated/derived flags) is source-agnostic. Adding **llm-d-prism** or **vLLM benchmark** data = a new `extract_<source>.py` producing the same corpus schema + a `source` tag on each point. The matrix gains a source facet; MAPE/SHAPE math is unchanged. Out of scope for v0.1.0 but the schema reserves it.

## 6. Decisions settled (from group discussion) and remaining open questions

**Settled:**
- **Hosting:** GitHub Pages + data committed to the Pages-served branch. No Go server, no RITS/OpenShift. *(was Q: deploy target)*
- **UI:** Overview page only, no plots — two tables (summary drill-down + points) with a totals/headline row and run-wide counts between them. `measured-or-resolved | all` tier switch; aggregates recomputed client-side so filters never show stale numbers. Built on `inference-sim/leaderboard/web`.
- **Comparisons:** all end-to-end via `blis run`/`replay`. Per-point data comes from **`cmd/signedprobe`** (already in the release — no `-json`, no upstream PR), the single source of truth; `metricscore` is a logged, non-blocking diagnostic only. Both built from source at the resolved tag.
- **Metrics (v0.1.0):** **mean TTFT + TPOT, MAPE + shape** — exactly what `signedprobe` emits. E2E, tail p99 and throughput are **not present in v0.1.0** (not shown, not gated), with a one-line "future" note; the unlocking work is post-0.1.0 (§4.3a, §7).
- **Default view = on-target `v0.31.0`** (the default filter *is* the headline). vLLM version is a per-row badge + filter, not a banded group.
- **No quality exclusions in v0.1.0:** `signedprobe` emits every point it can run; TTFT-spike / non-monotone-TPOT filtering is **not** reimplemented here (scoring logic stays out of the repo) — known artefacts are noted, not dropped. **Speculative (`mtp`) points are all `not_scored: no_acceptance_rate` in v0.1.0** (log-derived acceptance rate is post-0.1.0 — §7); never an assumed value. **Corpus is filtered to `framework: vllm` before scoring** (`signedprobe` has no framework flag; BLIS only models vLLM).
- **Multi-node:** a toggle, hidden by default; **may ship disabled** in v0.1.0 since enabling it needs a `blis-latency-kernel` change. Scored with the correct multi-node scenario when on.
- **Model identity (D7, corrected):** model is read from the server log / InferenceX config, never the display name; **no Llama-3.3 catalog entry is needed** (InferenceX's `llama70b` = retired Llama-3.1-70B-Instruct, which BLIS already has). vLLM version is a per-row badge + table filter, **not** a banded group.
- **Same-points delta (Q6):** every snapshot reports its change vs the previous one over the point intersection, so "did this BLIS release move accuracy?" is answered with the point-set change held out.
- **Noise floor (D6):** computed per row from InferenceX `std_*`/repeats, with the 1.6% corpus median only as a fallback.
- **Direct path only (Q7, Q8):** direct extractor + in-pipeline scenario generation, run at the `go.mod`-pinned kernel version, with all `signedprobe`/`metricscore` flags passed explicitly — including **`-scenarios` (no default; it errors without one)** — so nothing falls back to an AISimulate default. Failure semantics (Q10): nothing published on a failed/partial run.

**Still open:**
1. **End-to-end run cost.** The `blis replay` over every in-scope point, plus the ~34 GB dump restore, is the heaviest step. Hosted `ubuntu-latest` enough, or budget a self-hosted runner?

*(Not open for v0.1.0: per-point data sourcing — resolved, `cmd/signedprobe` from the pinned tag, no `-json`/PR (§4.3). E2E/tail/throughput — simply out of scope, revisited post-0.1.0 (§4.3a).)*

## 7. Build order for v0.1.0

- **M1 — Corpus + per-point export:** build `blis` + `signedprobe` + `metricscore` from source at the CI-resolved `$BLIS_TAG`; run the direct extractor + `gen_direct_*` (at the `go.mod`-pinned kernel) against the pinned dump; then `signedprobe -blis <built blis> -scenarios <generated> …` (all flags explicit) for the per-point **TTFT/TPOT measured+predicted** CSV. **Report from the real dump:** points on-target `v0.31.0` (settles the §6.3 default), `mtp` points lacking an acceptance rate, prefix-caching points, and the logged `signedprobe`-vs-`metricscore` gap **broken down by §4.4's three edge-sets** (partial-sweep, no-TTFT, prefix-caching tier). *(Pipeline verified end-to-end locally — §4.3.)*
- **M2 — `summary.json` + schema:** build the §4.4 drill-down tree from `signedprobe`'s CSV — compute MAPE + shape per point (facets TP/EP/precision/spec_method taken from the corpus file, not the CSV), aggregate client-side into the totals/model/…/topology nodes, both tiers, per-row noise floor, coverage + `no_acceptance_rate`, `known_artefacts`, same-points delta, `metrics: ["ttft","tpot"]`. Validate against this repo's local `schemas/summary.v1.json`. Assert self-consistency (re-aggregate the same CSV rows independently and match); **log** (don't gate on) the `metricscore` aggregate comparison, whose gap is the expected prefix-caching + partial-sweep points (§4.4). **No E2E/tail/throughput keys, no exclusion buckets.**
- **M3 — Nightly CI:** diff on `(blis_tag, ix_tag)` (catalog/registry derived from the release, recorded in provenance), dump restore + cache, direct path with in-pipeline scenario generation (Q7), same-points delta (Q6), commit `data/latest/summary.json` to the Pages-served branch; nothing on a failed/partial run (Q10).
- **M4 — Static Overview page (on `leaderboard/web`):** two tables — summary drill-down (model → workload → GPU → topology) with a **totals/headline row** (visible same-points Δ) and points (measured vs predicted per concurrency) — run-wide counts between them, `measured-or-resolved | all` tier switch, vLLM-version filter **defaulting to on-target**, multi-node toggle (possibly disabled), a one-line "E2E/tail/throughput: future" note, provenance header, last-successful-run timestamp, Download JSON; **client-side aggregate recompute** so filters never show stale numbers. No plots.

**Explicitly post-0.1.0 (adds the omitted metrics):** (a) carry E2E/tail/throughput — widen the harness `Observation` + `signedprobe`'s CSV on the predicted side AND the extractor `SELECT` on the measured side (both repos); (b) **extract the measured speculative acceptance rate** from the run's server log and thread it through the harness as `--speculative-acceptance-rate`, so `mtp` points become scoreable instead of `no_acceptance_rate`. Both are **format/behaviour changes inside the release** — they land on `inference-sim` + `blis-latency-kernel`, then ship in a *future* kernel release → BLIS `go.mod` bump → BLIS release. By the §4.4 version-lag rule they cannot appear in a dashboard scoring today's release.
